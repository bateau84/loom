### Source sufficiency comes before audit approval

[`LearningSources.resolve`](../src/learning-sources.ts) resolves only ledger, objective, objective-link, review-request and review-relationship records. [`EvaluatorExecution.execute`](../src/evaluator-execution.ts) supplies those through `preparation.source(memberKey, sourceIndex)` with its existing authorization checks. Authored records can contain useful original prose and full review mandates; observed tool records remain bounded metadata/digests. Neither a native-message/native-call link nor an external artifact reference causes its underlying content to be fetched.

`coverage: existing-stored-record` means exactly that record was returned. It does not mean a full original transcript, implementation artifact, tool output or delivered instruction was returned. [`loom_trace`](../src/session-trace.ts) retains excerpts and metadata, omits raw tool arguments/outputs and instruction bodies, and cannot replace those missing originals. Cross-Session context remains separately restricted in [the plugin](../src/plugin.ts). Export-shape preflight does not add exported content to the prepared chain.

Before any export, privately inventory source identities, owners, kinds, version/coverage availability and permission state without copying bodies. Then, under the applicable explicit source-inspection grant, map every necessary trajectory item to content actually retrievable through the selected route. Distinguish an authored completion/review statement from the original observed verification it describes. Essential unavailable content blocks this candidate; optional omissions remain explicit gaps. The source-content implementation gap is separate from whether an operator still has the originals.

**Proposed first-audit limits, requiring explicit approval:** one logical evaluation; concurrency **1**; at most **12 actual provider requests**, **120,000 cumulative input tokens**, and **16,000 cumulative output tokens** across the entire evaluation; **zero paid overage**; no automatic retry, provider fallback or restart resume; stop new work after **10 minutes**, with grant expiry **15 minutes** after issue. Tool continuations and any permitted auxiliary requests count against the same totals. Disable unnecessary title/compaction requests. Record the authority's exact token-counting semantics, including reasoning/cache use; reduce or revise the scope before approval if the selected method cannot fit.

These are proposed operator limits, not configuration defaults or proven enforcement. The authority must enforce the actual sends and resource totals, including native retries and continuity. A local timer, `max_tokens`, a declared policy reference, available subscription quota or an operator checkbox is insufficient. Uncertain consumption remains reserved after expiry/cancellation; it is not released on a timeout. If the fixed account's included-only boundary or resource enforcement cannot qualify, no real call is permitted.

**Suitability is not yet assessable:** the permitted corpus, effective prompt and exact provider token semantics are unknown. Cumulative input includes repeated context on each continuation; 120,000 input tokens across 12 requests would average only 10,000 per request. That arithmetic is not a proposed per-request limit. After authorized source inspection, estimate the actual repeated input plus method/tool overhead, reserve an enforceable upper bound on output including relevant reasoning, and count any auxiliaries. Cached tokens do not disappear from accounting unless the authority's approved semantics explicitly say so. If the corpus cannot fit, choose a smaller complete eligible objective or request revised, enforceable limits before inference. ## 3. Separate offline preflight from native source collection

The Python validator and local file hashes do not start OpenCode or request inference. Native inventory/export commands have an additional prerequisite: **use an explicitly named, already-running approved endpoint whose execution/recovery/schedule effects are independently fenced for the collection scope**. An idle UI or lack of a new prompt does not establish that condition. Do not start or restart a source host to collect evidence while its uncertain native work can resume.

This corrects the earlier unconditional no-inference description. On pinned OpenCode 2.3.0, both [`api`](https://github.com/anomalyco/opencode/blob/a6b15d33daf6ab7d35569f6d711fdb630b9f04e7/packages/cli/src/commands/handlers/api.ts) and [`session export`](https://github.com/anomalyco/opencode/blob/a6b15d33daf6ab7d35569f6d711fdb630b9f04e7/packages/cli/src/commands/handlers/session/export.ts) call [`ServerConnection.resolve`](https://github.com/anomalyco/opencode/blob/a6b15d33daf6ab7d35569f6d711fdb630b9f04e7/packages/cli/src/services/server-connection.ts). Without an explicit server it can start the service; [managed-server startup resumes durable execution claims and every server starts schedules](https://github.com/anomalyco/opencode/blob/a6b15d33daf6ab7d35569f6d711fdb630b9f04e7/packages/server/src/process.ts). The explicit `--server` branch checks that endpoint and fails if unreachable, without falling back to startup. It does not fence work already running there. `--standalone` and `autostart: false` are not substitutes: either can still start a server. This is source evidence, not a newly executed recovery test.

After separate approval to inspect/export the selected sources, verify the actual CLI/server/plugin/SDK versions and collection conditions above. Run from the checkout matching the qualified installation, substitute the real source identifiers and resolved files, and keep all outputs private. The following is conditional operator collection, not an executable production Evaluator route:

```sh

umask 077
: "${s3_approved_server:?Set the already-running approved native endpoint; no automatic startup}"
s3_private=$(mktemp -d /tmp/loom-evaluator-s3.XXXXXX)

s3_child_session=ACTUAL_SELECTED_SOURCE_CHILD_SESSION

  --param "location[directory]=$PWD" > "$s3_private/agents.json"

  "$s3_rubric_file" "$s3_model_settings"

  "$s3_child_session" --sanitize > "$s3_private/child.json"

  --parent-export "$s3_private/parent.json" \
  --child-export "$s3_private/child.json" \
  --report "$s3_private/source-preflight.json"
```

Repeat the export and `--child-export` argument for **every selected source child**, including intervening ancestry. The tool requires at least one child; do not fabricate a child to make an unrelated single-Session case pass. Its success establishes bounded export shape/ancestry consistency, not authenticity, completeness, authorization or source receipt. Sanitization is best effort; inspect exports privately before any transfer. Exports stay outside the repository and are not inputs to an unrestricted model command.

Do not run this block until export and temporary retention are authorized. On success or failure, retain or remove the owned directory and any partial exports under that exact policy; do not delete someone else's source or native history. If the endpoint is unavailable, stop instead of changing connection mode. No original-source command in this block was executed by the S3 blocker investigation.

Verify the actual installed plugin/SDK pair, source/package identity and effective agent configuration. Resolve inherited/project instructions and the selected model settings from the real host; source-file hashes alone do not prove instruction delivery. Before accepting the audit, require native evidence that the Evaluator actually loaded the installed Agent Run Audit skill and used the admitted method. Preserve the distinction between installed bytes, a skill-tool result, named host input and final provider exposure.

## 6. Independently assess the actual reasoning

Give an independent human assessor, or a separately authorized Reviewer, the original evidence and exact audit output before the producer's verdict. Require source citations for material findings and assess whether the Evaluator:

- reconstructs one objective across attempts, review findings, corrections and independently verified outcomes;
- distinguishes completion claims from verification and preserves each original review/recheck's actual scope;
- identifies useful practices as well as failures, necessary exploration and avoidable rework, without turning post-outcome instructions into evidence of prior benefit;
- explains mechanisms, alternatives and counterevidence, including the strongest evidence against its recommendations;
- identifies missing originals, chronology/independence uncertainty and source-coverage limits;
- recommends a justified, testable improvement or concludes that no change/insufficient evidence is warranted.

Challenge the assessment with the misleading early completion claim, partial runtime recheck and Stage 3 artifact-equivalence limitation present in the original trajectory. The audit must not turn those into unqualified full acceptance. Do not plant false originals or mandate a favorable finding.

Record separate verdicts for **deterministic implementation**, **installed mechanics**, **authority/account qualification**, **genuine original-work reasoning**, and **recovery/authorized result readback**, with exact artifact identities and unresolved gaps. Controlled recovery of a scripted result does not qualify recovery of a real authorized audit. One useful audit does not establish instruction efficacy, independent recurring patterns, full S4, Q4/Q5 or E11. Publish only reviewed redacted evidence; retain/delete private exports and receipts under the approved policy and remove the owned temporary directory when that work is complete.
