# Loom authority reconstruction — human surface and journey assessment

**Status:** Design analysis for accepted `docs/anchors/loom-authority-reconstruction/anchor.md`; not a replacement Anchor or implementation acceptance. Candidate-surface boundaries below incorporate the user's resolution of OQ `3fb7f28b-e116-4765-9366-d2a84c9f7222`.

## Human problem and intent

A developer/product owner wants to delegate software work without becoming its project manager, yet needs to understand what Loom is doing, inspect evidence, retain authority over real product choices, and recover when reality diverges from the plan. Too much ceremony makes autonomy unusable; too little transparency makes it opaque and potentially unsafe. This repository-grounded design hypothesis is not user research; actual user frequency, dashboard prominence, and appetite for direct Plan/workflow editing remain unvalidated.

### Experience goals

1. **Conversational, not procedural:** Think aloud and investigate without learning roles or choosing workflow mode.
2. **Legible delegation:** Resume after a gap and understand outcome, state, evidence, dependencies and next decision without reconstructing internals.
3. **Trustworthy recovery:** Failure, uncertainty and interruption are explicit; useful work remains visible; no false success or unsafe duplicate action.
4. **Proportionate control:** Routine expertise choices remain Loom's; people retain meaningful product, risk and scope choices.

### Realization principles

- Report user-relevant outcome/boundaries, not internal dispatch bookkeeping.
- Distinguish product Plan from execution steps; unknown/stale/conflicting data is not healthy zero.
- Consequential transitions have truthful observable state and safe re-entry; an attempt is not success.
- Conversation is the route for refinement/questions; observation does not imply execution authority.
- Prefer recognizable work names and progressive technical detail; preserve exact IDs for diagnosis/routing.
- Do not promise timing/progress the host cannot observe.

## End-to-end journeys and coupling

1. **Idea → conversation:** user describes goal/problem; Loom discusses and resolves technical/repository questions. Investigation is not permission to mutate (BR-019/020).
2. **Commit → accepted outcome:** user commits, material product ambiguity resolves, Loom chooses proportional process. Refinement returns through conversation, affects only relevant authority/work, then resumes (Anchor AC 1–3/26; BR-020).
3. **Outcome → reviewed Plan → (optional later implementation):** Objective/Phase/Wave/Task meaning must persist across Planner, Worker and gates. BR-021 makes plan context a human-relevant dependency: missing context can lose rationale, ownership or acceptance meaning. Under the user's accepted scope, a requested plan-only workflow may end at a reviewed Plan; this is an intermediate planning outcome, not Objective/product completion and not permission to implement. A later implementation request is a separate authority transition.
4. **Execution → evidence/state:** implementation, review, verification, acceptance and knowledge are distinct. Model claims, fake fixtures or local green checks do not equal real product acceptance (Anchor AC 8–11, BR-007).
5. **Failure → recovery/stop and record lifecycle:** evidence-led bounded recovery may proceed; exhaustion/no progress stops honestly with useful artifacts preserved and specific boundary. BR-008's explicit single continuation is not permission for repeated retries. Cancellation is not Archive or Permanent Delete. The latest requested journey allows Archive from any workflow state, with Active first cancelled and cancellation confirmed. If external operations may remain in flight, Archived must retain an uncertainty marker and relevant evidence; Permanent Delete is separately confirmed and waits for confirmed quiescence. Requested preservation covers project files, retained evidence/provenance, and completed work; current cleanup's deletion of OQ answers/attribution is a known mismatch, not a guarantee.
6. **Cross-session resume:** project, host session, workflow, plan, task and specialist contexts differ. Upgrade/legacy ambiguity must fail closed instead of guessing ownership (BR-017; `docs/user/upgrades.md`). Dashboard projection is read-only observation, not canonical execution authority.

Coupling: accepted intent constrains design/requirements; these constrain Architecture/Plan; shared Plan informs Worker/review/QA/OQ handoffs; evidence informs independent gates; lifecycle affects what can be cleaned/reopened; dashboard and conversation must agree without stale projection mutating canonical state. Users need not manage this graph, but the interface must not flatten its important distinctions.

### Cleanup: current implementation vs. user-approved boundary

There is a material **current implementation-vs-intended-behavior discrepancy** at the cleanup/evidence seam. In the current source, `plugins/loom/workflow-cleanup.ts:292–299` deletes the workflow's `oq-index/` entry and the entire `oq/<workflow-id>/` prefix as part of cleanup. This includes stored OQ records, including answered-question content and attribution; therefore current cleanup does not preserve all question-answer provenance. This is a source-backed description of current implementation, not evidence of deployment or runtime behavior.

By contrast, the user-approved cleanup boundary recorded in OQ `3fb7f28b-e116-4765-9366-d2a84c9f7222` was explicit-confirmation removal of terminal failed/cancelled workflow records while preserving retained evidence and completed work. Later user clarification extends the requested human journey: any workflow state can be Archived out of the default list; Active must first be cancelled; after confirmed cancellation, Archive may proceed despite a potentially in-flight host operation only when Archived preserves an explicit uncertainty marker and relevant evidence. Permanent Delete is separate, explicitly confirmed, and waits until quiescence is confirmed. Preserve project files, retained evidence/provenance, and completed work. The design records this latest direction without claiming the accepted Loom Anchor or implementation has yet been reconciled. Proposed BR-018 makes question-answer/evidence detail explicit in AC 16–17, but BR-018 remains **proposed**; its additional normative requirements are not independently accepted product authority.

US-004 and SC-004 describe the approved **desired user experience**, not proof that current cleanup meets it. Cleanup confirmation and outcome messaging must not imply that answer content/attribution survives until the discrepancy is resolved and verified. This is an inventory/design finding only: it is not a proven historical incident, a prevalence or deployment claim, or authority to repair product code within this design work.

## Bug and regression evidence, correctly bounded

1. Diagnostic has since verified bounded historical mechanisms from specific commit/regression evidence: pre-`cd4eac4` budget behavior lacked a fresh-user continuation for an exhausted unfinished target (the commit records an actual Worker deadlock; later continuation behavior/evals are commit-reported, not independently replayed here); `f337b9f` and its regression test show an answered cross-role blocking question could remain stuck because a consumer gate depended on aggregate closure; and the browser probe/regression evidence in `072137d` confirms malformed dashboard refresh data could poison the last-good snapshot and break navigation. The `8c5a0a8` publication case is **probable**, not confirmed in its exact lifecycle cause: evidence points to a missing session-local staged fingerprint being treated as changed bytes, while the cache-loss origin remains unknown. Broader scope/Git guard commits (`2047563`, `5d214f1`) establish code changes, not that each change fixes a user incident; dashboard cleanup commit `3c108aa` documents a feature, not a proven defect. These findings confirm only the bounded historical mechanism/evidence described—not incident provenance (except the deadlock recorded in its commit), frequency/prevalence, deployment, or current production behavior. Preserve them as scenario evidence, not product authority or additional guarantees.
2. `dashboard/review-regressions.test.ts`, `dashboard/review-regressions.e2e.spec.mjs`, and proposal `dashboard-refresh.md` list regressions: repeated wave IDs across phases, complete scope matching, same-destination link focus after rename, heartbeat refresh, long request text wrapping, leaving attention mode, producer-to-HTTP history markers and credential redaction. These expose candidate failure experiences: wrong identity, lost keyboard context, misleading freshness, clipped user context, confusing filter transitions, incomplete history and sensitive disclosure. Tests show regression coverage was deliberately encoded, **not** incident rate, deployed behavior or accepted scope.
3. Evals and deterministic tests are proxies for cases—not proof of model judgment, multi-process integration, interrupted-host experience or user comprehension. Preserve this evidence limit.

## Coverage and resolved user-owned scope

Initial inventory found no durable User Story/Design Scenario corpus. New `user-stories/` and `scenarios/` add a minimum cross-surface set traced to Anchor/accepted BR. Context assumptions are design hypotheses, not research findings.

The formerly open candidate-surface question was resolved in OQ `3fb7f28b-e116-4765-9366-d2a84c9f7222`: dashboard directory/session/workflow views are read-only inspection; the then-approved cleanup was explicitly confirmed and terminal-record-only; and Objective planning/plan-only is a reviewed intermediate outcome with no implementation authority. User answer to OQ `b3232418-978f-4209-bdbe-68f3c26814a1` further clarifies that after cancellation Archive may proceed with an uncertain in-flight operation only if Archived retains an explicit uncertainty marker and relevant evidence, while Permanent Delete waits for confirmed quiescence. This updates the requested cleanup journey, not the accepted Loom Anchor or current implementation. Other product/taste choices not settled by accepted authority remain user-owned; in particular, the prominence and interruption level of status notices are design recommendations, not additional user guarantees. The human journeys for delayed downstream OQ reconciliation and malformed dashboard refresh are captured in SC-005 and SC-006. These are regression-derived refinements, not new product guarantees or claims about incident prevalence.

## Accessibility and validation implications

Dashboard/dynamic conversation states need keyboard access and visible focus; stable focus when snapshots rename/update/disappear; text-backed status; understandable loading/stale/conflict/unknown/error; linear reading order and 320 CSS-pixel reflow; reduced motion; accessible names; exact cleanup target/consequence before destructive confirmation; no hover-only action; preservation of user-entered context. Validate actual running UI and representative journeys. Synthetic screenshots/fixtures cannot substitute for real publisher/browser interaction.

## Work lifecycle requests: requested experience vs. current capability

The lifecycle journeys below are a newly surfaced human-facing gap, not a claim that the current product supports them. Existing stories cover recovery after interruption and cleanup of terminal records, but do not cover deliberate backburner/pause, returning to paused work, safely revising earlier accepted work, or a competing unrelated request arriving while an execution is active.

- **Current documented behavior:** Dashboard `Pause`/`Resume` in `dashboard-refresh.md` only freezes/restarts automatic display refresh; it explicitly does not pause/resume Loom execution. `dashboard-experience.md` allows read-only inspection and only confirmed cleanup of terminal failed/cancelled records. `conversation-first-experience.md` describes refinement to the active objective, but does not define what happens when a new, unrelated request arrives. Current cleanup source deletes answer-bearing OQ records and attribution (see cleanup discrepancy above); do not claim that answers/provenance are currently retained.
- **User-requested lifecycle meaning:** Archive moves a workflow out of the default list for every state except that Active must first be cancelled and cancellation confirmed. After confirmed cancellation, an operation may still be in flight; Archive is acceptable only when Archived preserves an explicit uncertainty marker and relevant evidence. Permanent Delete from Archived requires separate explicit confirmation and confirmed quiescence. Project files, retained evidence/provenance, and completed work remain preserved. These are the latest requested journey semantics, not evidence of current implementation; the source-backed OQ-answer deletion means current cleanup does not meet the requested provenance-preservation outcome.
- **Scope/authority boundary:** The accepted reconstruction Anchor forbids product-code implementation in this effort. The earlier accepted Loom Anchor/OQ set bounded dashboard cleanup to explicit terminal-record removal, while the user's latest clarification expands the requested Archive/Delete journey. Record the distinction for General's authority reconciliation; do not imply this design task changed the accepted Anchor, claim these controls are live, or treat it as code authorization.
- **Journey added/refined:** US-005 and SC-004 capture archive state transitions, Active-first cancellation, retained uncertainty/evidence in Archived, and a quiescence gate before separate permanent deletion. SC-007 captures deliberate backburner/resumption for one chosen workflow and bounded backtracking without global pause behavior. SC-008 requires the specific original workflow to be confirmed paused before unrelated user work proceeds; it does not define system-wide pause/interruption. Across all scenarios, an unconfirmed in-flight outcome remains unknown; do not claim cancellation, pause, or data preservation beyond established facts.

This boundary is materially ambiguous only if the product must choose between putting lifecycle controls in the existing read-only dashboard and keeping them in conversation/another accepted control surface. No placement is prescribed here: preserve the existing dashboard boundary and route that material scope choice for explicit product authority before implementation. The journeys themselves are recorded without asking the user to choose routine interaction details.
