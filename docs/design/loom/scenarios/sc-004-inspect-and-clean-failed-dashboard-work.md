# SC-004 — Archive or permanently delete workflow records without losing useful work

**Context:** A developer using Loom across working directories wants to remove workflow records from the default work list without confusing that action with cancellation or destroying useful work. The view may contain active, blocked, failed, complete, or cancelled workflows. They may use keyboard navigation or a narrow viewport. This scenario reflects the user's latest clarification of the requested Archive/Permanent Delete journey; it is proposed human-facing behavior, not proof that the earlier accepted Loom Anchor or current implementation already supports it. Current implementation has a known source-level mismatch: `plugins/loom/workflow-cleanup.ts:292–299` deletes workflow OQ records, including answered-question content/attribution, despite the intended retained-evidence boundary. This is not a claim of historical incident or prevalence.
**Goal:** Remove any workflow state from the default list by archiving it, while preserving project files, retained evidence/provenance, and completed work; permanently delete an archived workflow record only through a separate explicit confirmation.
**Scenario:** The developer navigates to a workflow from the default list and chooses **Archive**. Any non-active state can be archived out of the default list into **Archived**. For an Active workflow, the person must first cancel it: the workflow remains in the default list while cancellation is pending or uncertain, and becomes eligible for Archive only once cancellation is confirmed. Archive and cancellation are distinct state transitions; neither deletes project files, retained evidence/provenance, nor completed work. Later, from Archived, the person may choose **Permanent Delete** as a separate action, review the exact archived record and preservation boundary, and explicitly confirm. The record is then removed from the ordinary workflow views; retained evidence/provenance and completed work are not implied to be deleted. Back/reload and an uncertain response must leave the person able to distinguish the last confirmed state from an unconfirmed transition.
**Failure / edge condition:** The workflow is Active, cancellation is pending, cancellation cannot be confirmed, the record changes while viewed, or projection is stale/conflicted; alternatively, the permanent-delete response is interrupted after possible completion. Do not archive an Active or in-flight workflow as if it were safely cancelled, silently broaden the permanent-delete selection, or report success/failure when outcome is unknown. Preserve the last valid view, label the known/unknown transition honestly, and provide a way to re-check it. Current cleanup code deletes answer-bearing OQ records and attribution, so do not tell the person that OQ answers/provenance are retained by current cleanup; the preservation outcome is a requested behavior and a known implementation gap. Historical cleanup regressions motivate testing identity/state drift; they do not imply incident prevalence.
**Observable outcome:** The person can distinguish Active → cancellation pending/uncertain → Cancelled → Archived → Permanent Delete, as well as direct Archive of other states. They know which transition is confirmed, what remains in the default list versus Archived, and that project files, retained evidence/provenance, and completed work are preserved by the requested path. Dashboard inspection itself remains read-only; Archive/Delete controls are requested behavior, not current capability or implementation permission.
