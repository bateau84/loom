# Understand a Session and its accumulated learning

The user starts with an ordinary Session. They should understand what was attempted, what changed, what supports the conclusion and what remains uncertain without creating an Action, Plan or historical objective.

## Experience

1. Select Session, Action or objective and state an evaluation question. Distinguish a recorded completion from a point-in-time cutoff.
2. Inspect original intent and scope. If the original user request is missing, label the available intent as authored reconstruction.
3. Follow a chronological or hierarchical engineering trajectory: assignments, failed attempts, findings, corrections, verification and abandoned approaches remain separate attributed records.
4. Open exact supporting originals before freezing. Show exclusions, source-owner denial/unsupported boundaries and missing evidence alongside the foundation. Empty evidence offers a useful preview without a broken freeze action.
5. Inspect conclusions with support and counterevidence. A narrow Wi-Fi verification cannot silently become verification of Ethernet or every network interface.
6. Follow accumulated increments and retained earlier concerns. Latest and earlier increments have stable labels; processing/caught-up state never claims completion. A resumed Session visibly has observed evidence beyond committed coverage.
7. Inspect learning activity separately, including failed evidence retrieval and resource counts. This is not the engineering trajectory.

## Presentation

Readable titles, attributed statements and meaningful dates precede UUIDs, hashes and raw JSON. Exact technical values remain in native expandable disclosures. Local navigation and source-to-finding backlinks have descriptive labels and visible focus. Requests for another authorized view are explicitly presented as requests, not fake network links or implied authority.

Use the shared history/interpretation models for JSON, Markdown and HTML. Rendering does not create domain state. HTML escapes all source content and has a restrictive content-security policy. Native details/summary, skip links, responsive reflow and keyboard focus work without application scripts. Reports explain a recommendation outcome such as “no new recommendation” without suggesting that no engineering change occurred.

## Acceptance evidence

The controlled ordinary-Session fixture includes failed restart, retained earlier concern, reported correction, scoped QA, abandoned polling, later continuation and a failed evaluation retrieval. A fresh reader must answer what was attempted/corrected, what remains unverified, why caught-up is not complete, which earlier original supports a concern, and whether later/evaluation activity entered frozen membership. Record extra/failed reads and resource costs; do not claim token savings from bytes.

Actual browser navigation is separate from static HTML checks. A synthetic scripted interpretation does not establish genuine Evaluator reasoning. The real historical Session and human validation gates remain open until exercised with authorized source access.
