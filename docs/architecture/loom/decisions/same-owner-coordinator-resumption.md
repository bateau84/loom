## Derived from

- Accepted bounded request `task:24eea0bc-8600-4924-8b17-23f1b1f55eac`: restore the **same** General's access to original workflow `e71579e4-2666-4b92-9243-2436a26295e9` after side repair `9fc34e84-c2b5-4713-ad2b-3a5ab1a9118d`, without replacement, ownership transfer or history loss.

## Satisfies

The bounded restoration request only. This is coordinator **access restoration**, not general pause/resume, recovery of uncertain operations, a new owner, a new execution attempt, or authorization to execute the original product work. It does not implement the broader lifecycle proposal in [BR-027](../../../requirements/loom/br-027-pause-resume-and-revisit-workflow-work.md).

## Decision question and evidence

How can the original coordinator regain its own workflow binding after completed side work without weakening membership checks?

Current `plugins/loom/runtime.ts:sessionBoundToWorkflow` checks one `session/<id>` value. `plugins/loom/index.ts` start creates a new workflow, records `createdBySession`, replaces that binding, clears step/OQ selectors and initializes new limits/budget. `assertSessionRebindingAllowedLocked` checks the prior binding but does not select an existing target. `plugins/loom/lifecycle.ts:workflowBindingTerminal` describes logical terminal state, not host execution liveness. No supported existing-workflow restoration surface was found. These are repository observations, not inspection of the two live workflows.

Additional feasibility evidence (2026-10-01):

- `runtime.ts:404-452,522-536` provides cross-process advisory exclusion both with and without a storage transaction. Plugin setup substitutes Loom's transactional, project-scoped, runtime-version-fenced storage (`index.ts:2974-2999`). These can protect a binding transition; they do not lock the host scheduler.
- `runtime.ts:1017-1042` keys child membership by the **child's** session, not the coordinator's current workflow. `index.ts:2678-2763` schedules OQ continuations against exact child/step/attempt bindings. Restoring the parent's pointer neither grants nor withdraws these authorities.
- `runtime.ts:2088-2201` distinguishes unused launch credentials, admitted launches and consumed attachments. Unadmitted grants can become discoverable by parent dispatch after restoration; admitted launches cannot be admitted again. Child consumption checks its exact grant, expiry and target rather than the parent's current binding.
- `index.ts:3467-3483` centralizes registered Loom execution, but its current entry check alone is **not** a binding-epoch fence. Parent delegation selects an active workflow before its later grant/budget transaction (`index.ts:10889-11006`). These are concrete integration seams to fence, not proof that current code already meets this revision.
- `evidence-admission.ts:27-85` retains admission origin and rejects proof attribution after attachment changes. `workflow-cleanup.ts:147-275` rechecks state and scans bindings within the workflow/work transaction. Reuse these seams instead of treating every late result as newly bound work.
- The supported [OpenCode V2 plugin contract](https://opencode.ai/v2/docs/build/plugins) exposes session scheduling, wait, interrupt and tool hooks, but no correlated host-wide admission/idle lease. Synthetic scheduling returns an admitted inbox item; prompt hooks omit synthetic/shell/control messages, and captured tool snapshots remain executable. No host-idle or tool-list inference is used below.

## Drivers, options and comparison

| Option | Benefit | Cost, failure mode and authority consequence |
| --- | --- | --- |
| Dedicated same-owner rebind command with scoped coordinator fencing (selected) | Keeps start/create semantics and ordinary membership checks unchanged; supported Loom-only transaction; compatible with independent child work. | One small public surface plus coordinator admission fencing. Must preserve grants and fence stale selectors, not just write one key. |
| Add an existing-workflow mode to start | Can share the same safe rebind transaction and need no separate tool name. | Overloads create/restore inputs and responses; accidental reuse of creation initialization can reset budget or attach a new workflow to the Objective. Viable with strict separation, but less clear and no smaller correctness boundary. |
| Binding-epoch checks at every coordinator mutation/return instead of an invocation lease | Also viable with exhaustive commit-time checks; permits more same-session concurrency. | Many dispersed tools, implicit active-workflow reads and host admission paths must each propagate a captured epoch. Easy to miss a side effect before validation. More invasive than a shared outer executor boundary; retain epoch checks for delayed results, not as the sole mechanism. |
| Host-wide source/target idle barrier (previous choice) | Could establish absence of all queued/executing activity if the host provided it. | No supported fence exists. Requires another component and stronger semantics than access restoration needs; rejected, not deferred behind a denial-only implementation. |

The first two retain one current binding and require the same ownership, atomicity and non-amplification proof. The shared invocation lease wins over distributed commit checks because it uses existing advisory locks and a central registered executor. A binding stack, multiple simultaneously authorized workflows, owner-ID fallback in every tool, raw storage editing, and creating a replacement are not alternatives within this request: they expand authority or fail identity/history preservation.

## Decision and interface

Expose `loom_resume({ workflowId, fromWorkflowId })` to General, with equivalent native and Code Mode behavior. `workflowId` selects the existing target; `fromWorkflowId` is an explicit compare-and-swap expectation for the current binding. Neither grants authority. There is no caller-supplied session/project/owner, force flag, grant, release, cancellation, reopen, or budget override. Host caller identity and project epoch supply scope.

Success returns `status=resumed`, source and target IDs, and an explicit statement that only coordinator access changed and no work was dispatched. An already-current, same-owner target returns `status=already_current` without mutation; it does not attest quiescence or execution readiness. This no-op still checks caller/target provenance, project, lifecycle and association validity, but does not require a completed current target or scan grants for a transition it will not perform. A repeated request after a lost response may use this outcome, but cannot switch away from an intervening different current workflow. Denial gives a bounded reason (ownership/project mismatch, stale source/admission, incomplete source, outstanding unused grant, conflicting transition, unavailable/inconsistent state/runtime), without disclosing another project's workflow contents. Unknown **authority/state** fails closed; unknown host liveness is not an eligibility input. No automatic retry or fallback to start.

### Admission and preservation invariants

1. **Same coordinator, not transfer.** The effective caller is the host-authenticated General coordinator, not a specialist/child relabelled General. Both source and target canonical workflow records belong to the current project epoch and have `createdBySession` equal to that exact caller session. Durable original creator provenance authorizes selecting the target despite the displaced current binding; a supplied UUID, shared Anchor/Objective, transcript claim, parent relationship, or current ownership of the repair is insufficient. Missing/conflicting provenance fails closed; do not manufacture it from legacy fallback. No binding of another session is changed.
2. **Completed source.** For an actual switch, the current binding must exactly equal `fromWorkflowId` and name an existing, successfully completed workflow: nonempty steps all complete/passed, no cancellation, deletion/archive fence, or unresolved lifecycle inconsistency. A failed gate, a mere release marker, an empty/unrouted workflow, or no runnable steps is not completion for this narrow command. The completed repair is eligible **only if it is still the current binding**. If another repair/restoration workflow has since become current, that exact workflow must finish and be named instead; do not silently hop via the historical repair.
3. **Existing target.** Load only from the current project namespace; reject cancelled, deleted, archived, malformed or conflicting target state. Restore its existing status unchanged, including failed gates or blockers that need normal recovery later. No need for a runnable step, no inference from pending status, and no implicit unpause/reopen. Any Objective/Plan association must still resolve consistently to its existing generation and membership; conflicting or missing associations deny, not migrate/reclaim.
4. **No authority amplification; no host-quiescence requirement.** Do not switch while either workflow has an unexpired, unrevoked, unconsumed, **unadmitted** dispatch grant. Scan all pages of scoped durable grants and validate their shape; malformed relevant authority is an error, not evidence of expiry. This preserves the prior unused-credential blocker without requiring host activity telemetry. In particular, restoring the parent pointer must not make a previously inaccessible unused target launch credential discoverable. The command does not revoke, renew, consume, reissue or otherwise repair any grant. Already admitted launches (including unconsumed/uncertain ones), consumed attachments, queued child OQ continuations and executing child tools do **not** block merely because they exist: they use their own unchanged authority, and uncertainty about their external outcome remains uncertainty. Consumed/revoked/expired grants remain historical and cannot become usable. No restart, dashboard heartbeat, empty local map or idle snapshot is needed or accepted as authority proof.
5. **Atomic binding and scoped admission fence.** Serialize the caller's coordinator binding-dependent Loom invocations with a project/session-scoped OS advisory lease, and serialize the transition's state transaction with both workflow identities and any associated work records. Re-read ownership, exact current binding/attachment, successful source completion, target lifecycle, grant eligibility and associations under those locks. Competing parent start/attach/resume and dispatch admission must share the coordinator boundary; child mutations and lifecycle changes share the existing exact workflow/work/step authority boundaries. No pre-lock snapshot authorizes the write. Canonical lock order, transactional persistence and runtime-version fencing are required. Readers after a crash see either the complete old binding or the complete new binding, never mixed selectors. See the realization boundary below; this fence excludes conflicting **Loom effects**, not all host execution.
6. **Bounded effects.** Atomically replace only the caller's current workflow binding, rotate its attachment identity and clear its step/OQ/attempt selectors. Record durable bounded transition provenance (caller/project, source/target, time and transition identity); ordinary workflow ordering revisions may advance for that metadata. Preserve exact workflow IDs, creator, accepted authority, Objective identity, Plan generation/revision and content, Task bindings/results, claims/receipts, step attempts/statuses, OQs/reconciliation, evidence/proofs, scopes, budgets/limits/dispatch history, and all independent gate results. Preserve grant records and their expiry/consumption/revocation semantics; no grant is renewed or made eligible by rebinding. Do not initialize defaults or call workflow creation/Plan compilation as recovery. No child attachment or stale attempt becomes current through this operation.
7. **After restoration.** Normal bound-workflow status and owner tools become available; each later dispatch, mutation, gate and recovery action still passes its existing checks. No child is launched, notified, replayed, reassigned or resumed automatically. Exhausted targets remain exhausted; failed reviews remain failed. Broader product execution still requires its own accepted authority.

Preservation means **no changes caused by resume** outside the listed binding/provenance/order delta. An independently authorized child may legitimately complete or add evidence immediately before or after that transaction. Resume must neither overwrite its result from a stale snapshot nor claim that the whole host remained unchanged.

### Realization boundary and concurrency cases

Use the existing advisory-lock primitive **without opening a storage transaction for the whole invocation**. The coordinator lease is outermost; existing workflow/work/step transactions remain short, canonically ordered inner sections. Never acquire a coordinator lease while holding a workflow/work/step lock. The shared registered Loom executor must cover native and Code Mode entrypoints, not only model/tool visibility or a native before-hook. Hold the lease from authoritative admission through all binding-dependent effects of the invocation and release on every return/error. This includes start, resume, attach and other same-session tools that infer their target from the current binding. Nested internal helpers use the already-held lease rather than reacquiring it. No child session lease is taken by resume.

Capture the invocation's binding/attachment tuple coherently before waiting for the lease and revalidate it after acquisition; a changed tuple denies the stale invocation rather than retargeting it. The newly rotated attachment identity prevents an A→B→A binding ABA. A call that has not yet entered Loom admission has no earlier Loom authority: on entry it receives the then-current binding and all normal checks. Host/model queue age is not a transferable execution credential. Hooks or adapters that already selected a workflow before entering the common executor must carry that captured tuple, never replace it with a later read. The test suite must exercise both surfaces and this waiting-call case.

Parent subagent permission admission (`index.ts:10889-11006`) must acquire the same session lease **before selecting the active workflow**, retaining it through exact grant/budget admission and construction of the allow/deny decision. If an earlier hook stage captured binding authority, revalidate its tuple too. Once a launch is durably admitted to its exact workflow/step/OQ, later host scheduling/attachment needs no parent lease: it is not allowed to select a different target or admit that grant again. Resume never schedules such work itself. Conversational Research/Diagnostic remains advisory under its existing rules, not a bypass into restored product work.

Binding writers outside the registered executor (legacy migration and workflow deletion/cleanup) must remain ordered against resume through their workflow locks and transactional current-binding checks; stale session enumeration must never delete or change a newly restored binding. Do not migrate legacy creator provenance within resume. Inventory these paths in implementation review. Continue to validate late evidence against its **original** admission identity (`evidence-admission.ts`), never against whatever the coordinator now selects. External effects already launched are neither undone nor replayed by resume.

| Concurrent condition | Required handling |
| --- | --- |
| Same coordinator's binding-dependent invocation or delegation admission | Orders before resume under the session lease, or waits and rejects its changed admission tuple. Never retargets a source call to the target. |
| Competing start/attach/resume | Same session boundary plus exact source/epoch CAS; at most one conflicting transition succeeds. |
| Source is reopened, cancelled or otherwise ceases to be successfully complete before commit | Deny on locked re-read. A subsequent separately authorized lifecycle change is not retroactively undone. |
| Target cancellation/deletion, association change, or other eligibility-changing mutation | Orders under workflow/work locks; if it precedes resume, revalidate and deny as appropriate. If it follows, its normal authority still governs. |
| Target step pending, active attached child, child write, valid admitted launch, OQ notification queued/in flight, unknown external-operation completion | Not a blanket blocker. Preserve the existing child's grant, attempt, binding and scope; exact workflow/step locks and normal admission checks govern its own effects. Resume does not infer execution readiness or issue a continuation. |
| Child completes/answers OQ/adds evidence during restoration | Serialize the relevant storage effects, preserve both changes, and attribute evidence to the original child admission. Do not restore a prior target snapshot. |
| Unused unadmitted grant in source or target | Deny without modifying it. Later eligibility may follow natural expiry or independently authorized ordinary lifecycle action, not resume's own cleanup. |
| Missing/corrupt authority, unavailable lock or transactional storage, incompatible runtime | Deny. These are actual safety prerequisites, unlike host activity observations. |

Thus **no ongoing target computation must finish merely to let its unchanged owner inspect/manage the workflow again**. Only an overlapping authority/state transition needs exclusion or revalidation; an unused launch credential needs the explicit non-revival guard. This changes no child recovery, retry, cancellation, retention or failure policy and introduces no Specifier-owned semantic decision. If implementation discovers that any child actually derives authority dynamically from the parent's pointer, stop and route that concrete seam rather than expanding this assertion to cover it.

## Consequences

One additive control-plane command repairs access without changing ordinary authorization. The price is same-session Loom invocation serialization and an audit of binding/delegation ingress, not a new host scheduler, activity ledger or cancellation protocol. Other sessions' independent child work remains concurrent. An unused grant can temporarily deny restoration; it is not silently invalidated. No ownership migration or stack schema is needed. Advance runtime compatibility fencing as needed so older writers cannot bypass the new transition boundary; activation must not reset any workflow/Plan state. Restoring access is reversible only through another separately eligible controlled transition, not a hidden rollback of execution history.
