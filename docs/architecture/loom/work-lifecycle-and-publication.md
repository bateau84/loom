This document supplies no implementation authorization.

## Current boundary and problem

The present Plan compiler creates Worker-only `task:<id>` nodes (`plugins/loom/workflow.ts`, `applyTaskPlan`); a role named in Plan prose, an OQ answer, or a pre-existing route step does not by itself constitute execution of that Plan Task. The current shell policy is a conservative allowlist, not task-scoped arbitrary-command elevation. `loom_scope_elevate` expands project-local **write paths** and has a one-use user path for hard boundaries; it does not grant command authority. Current workflow state has cancellation and step reopen, but no workflow pause, backburner, resume, archive, or operation-quiescence protocol. Cancellation revokes new activity but cannot undo an already admitted external operation. Current dashboard cleanup only deletes terminal failed/cancelled execution records and `plugins/loom/workflow-cleanup.ts` deletes `oq/<workflow.id>/` including answered content and attribution; completed-Wave receipts block deletion. Neither this behavior nor older terminal-only cleanup prose proves the proposed all-workflow archive/permanent-delete and historical-provenance requirements.

The design must compose four distinct questions: **who can decide/execute**, **what command can run**, **when a workflow may initiate new work**, and **whether prior host work has actually finished**. A lifecycle label must never answer the last question by inference.

## Forces and options

| Option | Mechanism and benefits | Cost and failure analysis |
| --- | --- | --- |
| Reuse canonical control-plane workflow/work transactions, add explicit role bindings, command grants and operation receipts, and maintain a distinct archived record view | Existing identity, locking, attachment, evidence and projection seams enforce a single authority chain. Per-workflow admission fences compose with grant issuance, step completion, lifecycle and deletion. | Requires transactional changes across several modules and migration/fencing of legacy records. An operation admitted before a transition may finish later; receipt reconciliation and conservative unknown state are mandatory. A stale publisher needs a deletion/archival visibility fence. |
| Separate lifecycle/command service with its own state and dashboard command queue | Could isolate a host executor and keep dashboard code thinner. | Dual sources of truth make pause, cancellation, scope and external-operation races harder to close; cross-store claims/confirmation and projection lag could declare false quiescence or publish out-of-scope changes. The extra service has no accepted availability/remote-execution obligation to justify it. |

Choose the first, **subject to an explicit admitted-operation boundary**. For commands, two viable realizations are typed operations through bounded adapters (simple ownership/effects proof for known Git and file actions, limited initial coverage) and a contained general executor with enforceable effect envelope and process-tree observation (broader command coverage, higher containment cost). Use adapters where adequate and an executor where actual effects can be established/enforced; neither initial adapter coverage nor command spelling is a permanent capability prohibition. An uncontained generic shell is not a viable substitute: lexical path checks cannot constrain arbitrary subprocess or host effects. When automatic containment/ownership proof is missing, route the request and disclosed uncertainty to the explicit User boundary, not to a command-name blacklist. User approval does not make an unenforceable effect envelope safe or prove host quiescence. No new remote service or dashboard-as-command-bus is warranted.

## Ownership and structure

- **Plan/work and workflow control:** persistent Plan generation owns semantic obligations and Task dependencies; the workflow control plane owns validated accountable-role-to-executable-slot bindings, scoped gates, current lifecycle state and attempts. At planning-only review, prove whole-Plan role/path feasibility against implemented/enabled capabilities, including later Waves, without dispatching Tasks or closing the Objective; a merely proposed route cannot PASS. At delivery admission, bind each unclaimed Task contribution to its **dedicated** role step, independent reviewer gate, or explicit user-decision wait before claiming the Wave. Do not reuse a fixed route step as a new planned Task's result: earlier reviewed route work may support an independently evidenced `already-satisfied` obligation only when it truly discharges that accepted work; otherwise plan the remaining role-owned contribution. Mixed-role dependencies and independent review gate downstream completion, including zero-Worker Waves. See [Role-Safe Plan Execution](role-safe-plan-execution.md). No historical Worker result is retroactively converted into specialist authority.
- **Command admission:** an attached exact step/attempt proposes a rejected operation's purpose, executable shape, targets, expected effects and recovery basis. Admission resolves actual targets (including symlinks and Git refs), checks task/product authority separately from path scope, identifies affected state and its owner, and establishes recoverability. A control-plane grant binds workflow, task, step/attempt, session, operation/effect envelope, target identities, limits, ownership/recovery evidence and any exact User approval; it is not a reusable shell permission. Automatic elevation requires effects contained within workflow-authorized, Loom-owned/recoverable state: removal of identified Loom-owned generated files can qualify even if destructive-looking, while an in-path write destroying unrelated bytes does not. Unrelated user data, shared/other-owned branches, host-wide state or unestablished ownership/recovery requires explicit User authorization before execution; General can only route the request. Approval covers disclosed effects, not new product meaning or unrelated tasks; denial, silence and ambiguity leave the operation unexecuted. Revalidate targets, ownership, recovery and effect envelope under appropriate guards at execution; changes require a fresh decision. Grants expire on pause, cancellation, reopen, reroute or changed operation/effects; already admitted work remains in the host-operation register. `loom_scope_elevate` is a distinct path-mutation mechanism: it cannot grant shell authority, and project-local path elevation alone proves neither ownership nor recovery.
- **Git publication:** the same task/attempt authority and exact admitted-byte provenance governs staging and commit. A controlled Git interface stages only eligible paths/fingerprints rather than granting generic `.git` write access; commit rechecks the full index and author identity against that attempt. To automatically admit abort/reset of Loom's own failed rebase, establish exclusive ownership of the operation, affected index/worktree/refs and a usable recovery point. To automatically admit force-with-lease to an exclusively Loom-owned delivery branch, establish branch ownership, the exact expected remote ref, all local/remote effects and a practicable recovery point. Shared/other ownership or uncertain remote recovery requires explicit User authorization; lease failure never licenses a retry against a changed ref without a new decision. Neither `reset` nor `force` is approval by spelling, and ordinary commit is not exempt from effect checks. Commit during progress; when origin exists, attempt push and record remote success separately from local commit. Missing origin, rejected push, authentication failure and uncertain remote outcome retain the local commit and truthful unpushed/unknown status; inspect remote result before retrying an uncertain push rather than claiming success. At conclusion PR creation is optional with origin and records only confirmed creation. No workflow lifecycle operation rewrites committed work.
- **Lifecycle and host-operation register:** a transactional per-workflow initiation fence prevents *new* dispatch/tool/command admission once an exact workflow reaches its confirmed pause boundary or cancellation. Before allowing unrelated user work, the coordinator obtains and checks that specific original workflow's durable pause acknowledgement (identity, revision and fence), not merely a global session signal. Each admitted external operation carries a durable workflow/attempt identity and an inspectable outcome/quiescence status independent of the workflow lifecycle state. An already admitted operation can outlive pause/cancel; an unobserved or indeterminate outcome stays explicitly uncertain in **every** view/state, including active, paused, cancelled, resumed, terminal and archived. A transient tool-call return is not proof that a spawned host/remote process stopped. Quiescence is established by outcome/termination evidence appropriate to the operation; when the executor cannot observe that, leave it unconfirmed and block Permanent Delete rather than guessing a timeout. No hidden background operation is implied or silently allowed by a transition.
- **Archive/provenance boundary:** canonical workflow records, archived visibility and historical provenance are separate concerns. Archived workflows leave the default dashboard view but remain inspectable in an Archived view, with unresolved-operation marker and supporting evidence intact. Ordinary Delete may mean Archive, not record destruction. Answered OQ text, source/attribution, evidence/claims and completed work must remain workflow-attributable historical records without active OQ routing. Permanent Delete removes the workflow record from both views, not the protected material; retain a minimal scoped deletion fence/tombstone so stale snapshots and old sessions cannot reanimate it. Preserve project files and durable work receipts; do not use the current cleanup's whole OQ-prefix deletion or its completed-Wave deletion prohibition as the proposed target. Historical reads cannot grant work admission. Browser control continues through the authenticated bounded canonical control path, never projection-file writes.

## Lifecycle transitions and invariants

| Transition | Preconditions / atomic boundary | Result and independent truth |
| --- | --- | --- |
| Active → paused/backburnered/yielded | Exact workflow identity; serialize initiation fence with command/tool/dispatch admission; record reason, revision and pause acknowledgement. | No *new* work from this workflow until resume. Outstanding operations may remain unknown; show marker/evidence. Intermittent issue and deliberate backburner remain distinguishable reasons, neither completion nor cancellation. Yielded unrelated request may proceed **only after** acknowledgement of this original workflow. |
| Paused → resumed | Explicit user choice or resolved pause condition within accepted authority; revalidate binding/role grants, Plan/dependencies and each interrupted operation's outcome before dependent execution. | Preserve history and previous proof; uncertain operation is not blindly repeated and dependent work stays blocked. Re-admit only still-authorized fresh work. |
| Any work → backtracked | New evidence/correction identifies affected node and dependents; fence current attempts and invalidate affected proof/bindings at a reviewed correction boundary. | Superseded attempts/history remain attributable; unrelated completed nodes remain intact. New product meaning or implementation scope still needs its owning authority. |
| Active → cancelled, then Archive | User-authorized cancellation/revocation of further workflow admission precedes Archive. Transactionally recheck lifecycle/project/revision and preserve operation register/provenance. | Archive may proceed with outstanding operation uncertainty only when Archived view carries its marker/evidence; cancellation is **not** quiescence. No false success if revocation fails. Already non-active workflows can archive without inventing a new cancellation. |
| Archived → Permanently Deleted | Explicit user confirmation of permanent **record** removal; cancellation/revocation if still active; confirmed quiescence of all previously admitted external operations regardless of current workflow state; protected-history retention verified before transaction commit. | Remove operational workflow record/views only. Preserve project files, evidence, answered-question attribution and completed work. Missing approval, uncertain quiescence, failed evidence migration or stale revision leaves archive/marker inspectable and operation unreported as successful. |

Pause is not a hidden host-process kill or a synonym for quiescence. A host/tool already admitted before the fence may return later, but its result must not automatically satisfy a now-paused or cancelled step; on resume it is reconciled against the current attempt and accepted scope. Cancellation revokes further authority, not project bytes, and Permanent Delete cannot be made safe by merely waiting for a timer or switching lifecycle labels. A late observation must remain attributable even if its original workflow moved from the default view. Use project/workflow locks and optimistic revision checks for admission and archive/delete so a concurrently changing record cannot pass a stale precondition; failure rolls back the mutation. A deletion fence must outlive stale publisher/session snapshots.

## Trust, failures and composition proof

Commands execute with host authority; untrusted command strings, symlink escapes, working-directory changes, subprocesses, Git hooks, remote origins and browser requests cross boundaries that the ordinary edit scope does not contain. Protected assets include unrelated user files, index/worktree/ref contents, remote refs, host-wide state and credentials. Before automatic admission, require canonical effect-target identity, exact task/path authority, established ownership/recovery evidence, and enforcement/observation appropriate to hooks, spawned processes and remote effects. Dynamic effects not proven contained require explicit User authorization for the disclosed effects; approval never proves the host operation has finished. If even the approved operation cannot be bounded to approved effects or its continuation cannot be accounted for, leave it unexecuted and report the technical constraint rather than laundering it through `loom_scope_elevate`. Local dashboard token/Origin checks mitigate browser CSRF, not shared-host identity; retain the existing network boundary. Credentials and raw output do not belong in dashboard projection; projection is display-only and must not decide lifecycle or quiescence.

The key falsification cases for separately authorized implementation are: an unavailable specialist role or missing independent gate passes Plan/Wave review; an operation is permanently denied just for its name; owned generated-file removal, own failed-rebase abort/reset or recoverable force-with-lease to an exclusively Loom-owned delivery branch demands User approval solely for looking destructive; unrelated data, shared/other-owned branches, host-wide or uncertain ownership/recovery effects execute with General-only approval; changed target/ref bypasses revalidation; an unobserved hook/subprocess exceeds its effect envelope; a local commit is reported pushed without a remote receipt; unrelated work starts before **this** workflow acknowledges pause; a paused/cancelled/archived workflow hides an unresolved external operation; resume duplicates uncertain work; a cancelled workflow is treated as quiescent; a stale dashboard record reappears after deletion; or removal drops an answered OQ's provenance. Prove the whole composition, not only isolated helper behavior: two concurrent sessions racing admission/pause and index/ref ownership, child return after cancellation, role handoff with Worker implementation and Reviewer proof, no-Worker Objective and planning-only Plan, all-workflow Archive (including active cancellation), and Permanent Delete with both unknown and confirmed quiescence. Verify exact effects, recovery points, User approval receipts, project files, durable evidence/provenance and completed work before/after each destructive transition; require truthful failed/uncertain outcomes. These are **future implementation verification targets**, not current test results.

## Open boundaries

No precise universal operating-system guarantee of terminating arbitrary host/remote work is established by accepted authority or current runtime. The proposed implementation must either track a bounded executor to confirmed quiescence or expose unresolved uncertainty indefinitely and refuse Permanent Delete; it may not invent a product-visible automatic timeout/retry policy. Exact UI copy and interaction for pause/Archived confirmations belong to Designer. Accepted user authority remains required for any material semantic change, including Anchor acceptance; a reviewed proposed Anchor is not self-accepting.
