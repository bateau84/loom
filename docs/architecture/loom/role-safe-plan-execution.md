**Status:** proposed; this design does not describe a current runtime capability.

## Derived from and satisfies

- [Accepted Loom Anchor](../../anchors/loom/anchor.md), especially first principles 1–4 and acceptance criteria 3, 6–11, 30 and 33. Criterion 8 governs accountability and unavailable ownership.
- [BR-024](../../requirements/loom/br-024-preserve-authority-ownership-through-handoffs.md) and [BR-021](../../requirements/loom/br-021-preserve-holistic-plan-context.md) are proposed refinements, not independent accepted product authority.
- [Work hierarchy](work-hierarchy.md), [control plane](control-plane.md), and existing scoped review, OQ, evidence, budget, cancellation, and project isolation contracts remain in force.

## Decision question and current boundary

How can a mandatory Plan Task be admitted, dispatched, reviewed and completed by its actual accountable role without interpreting Worker execution, an OQ answer, a fixed earlier route step or a model summary as a specialist decision? The persistent Plan owns semantic decomposition; the control plane owns executable bindings. `TaskSpec` and the persistent semantic Task currently carry no accountable role. `applyTaskPlan` in `plugins/loom/workflow.ts` makes every `task:<id>` a Worker step; `plannedTaskSteps`, `executableTaskPlanFingerprint`, `loom_complete`, Wave claiming/roll-up, review receipts and status projections assume those steps are Worker completions. Merely extending the Planner prompt or adding an owner label cannot satisfy the Anchor.

This decision covers Objective-depth Plan Tasks and their bounded Wave execution. Simple non-Plan maintenance remains on its route-built path. No change here authorizes new product meaning, substitutes a user decision, retroactively reclassifies old history, or claims that today's Worker-only runtime already supports role-safe Plan execution.

## Forces and alternatives

| Option | Mechanism and advantage | Cost, failure and authority boundary |
| --- | --- | --- |
| A. Dedicated contribution for each planned Task (selected) | Bind each Task to one exact role-owned `task:<id>` step; Worker Tasks keep their existing step identity. Review Tasks bind to a scoped reviewer gate; user decisions to a non-agent wait. A specialist-to-Worker transfer is two Tasks linked by a reviewed dependency, unless specialist authority was already discharged and evidenced before planning. Attribution, freshness and completion remain one-to-one. | Additional role steps and intermediate gates for cross-role dependencies; Plan schema, compiler, roll-up and projections all change. Cost is bounded by current per-Wave Task limits and existing dispatch budgets. Failure to instantiate the correct role/gate blocks admission. |
| B. Reuse fixed route steps when they appear related, otherwise create role steps | May avoid another specialist invocation when already-routed work is genuinely the planned deliverable. | Requires an exclusive, versioned Task-to-fixed-step binding, evidence partitioning, and review provenance across a step potentially completed before the Plan existed; shared steps are especially ambiguous. Reopen and amendment must not reinterpret prior authority. If strict enough to be safe, it offers little advantage over recording already-satisfied obligations and using A for new work. |

Both can implement real role paths; A is the smaller complete mechanism once evidence/attempt/review isolation and recovery are counted. Do not implement B opportunistically. An earlier reviewed specialist result may instead be cited as **already satisfied** in the obligation map with actual authority/evidence and reviewer-checkable provenance, not attached to a newly minted Task as its completion. If it does not exactly discharge the obligation, plan the remaining specialist work. A role label without dispatch or a promise to add a route later is not a viable third option.

## Structure and contracts

1. **Semantic Plan.** Each planned Task has one accountable role and bounded responsibility (`produce`, `execute`, `review`, or `obtain-user-decision`) inside accepted authority and the available role registry. Keep role/responsibility in immutable Plan revisions, not just executable TaskSpec. Multi-role work is decomposed into separate Tasks with explicit handoff edges; a single Task cannot silently change owner halfway through. The handoff names the source result/evidence, receiver's remaining work, and dependent acceptance condition. Routine work may be owned directly by Worker. An obligation marked already-satisfied requires an exact prior result and accepted-authority provenance; `authorized-defer`/out-of-scope uses its existing authority check and is not a runnable completion.
2. **Feasibility versus execution.** Whole-Plan planning-only `review-plan` checks every mandatory obligation, including later Waves, against a **currently implemented and enabled** route for the named role/responsibility and required independent gate, or an explicit supported user-question/acceptance path. It records an exact semantic Plan fingerprint and feasibility receipt; no Task slot, Wave claim or execution authority is created. A proposed design, hypothetical future agent, or Worker-only compiler is not a supported route. Delivery rechecks capabilities and exact current Plan at Wave admission; prior planning-only PASS never authorizes a Task. If capability disappears, stop affected admission and report the exact missing role/path.
3. **Executable Wave binding.** Planner's compiled current-Wave contract repeats role/responsibility from semantic Task and identifies its supported route, dependencies, verification and starting scope where relevant. Control plane validates equality against current Plan generation and Wave fingerprint, enabled agent capability, authorized responsibility, downstream independent review, and dependency acyclicity. In one serialized unclaimed-Wave transition it creates a pending `task:<id>` step with `agent=<role>` for producer/executor Tasks, a distinct Reviewer gate over named producer results for review Tasks, or an explicit non-agent decision wait for a genuinely user-owned item. It persists Task ID → exact step/gate/wait, role, responsibility, generation, Wave, semantic fingerprint and gate scope. No slot implies no admission. Dynamic role steps use the same attachment, scope, grant, observation, commit, budget and cancellation fences as fixed steps; they are not run through privileged generic Worker delegation. Decision waits grant no agent permission; General presents and records only the user's actual answer/acceptance on its existing exact user-authority path.
4. **Independent pre-execution review.** `review-plan` receives whole Plan and complete compiled role/slot graph with actual current-Wave contracts. Reviewer attachment binds to review attempt, generation, semantic Plan revision/fingerprint and executable graph fingerprint **including role, responsibility, slot type, gate edges and scope**. PASS revalidates values and enabled capabilities under Wave-claim transaction; FAIL leaves Wave unclaimed and nodes unrunnable. Compiler output alone never claims a Wave. An unrelated unclaimed Wave amendment may preserve an unchanged admitted Wave fingerprint; an affected Wave amendment, reopening review, or invalidation revokes unclaimed binding/verdict. No authority check relies only on a mutable prompt label.
5. **Result and handoff.** An agent's result is tied to exact attached step attempt and current Plan binding, with summary, evidence references and durable artifact/decision reference where applicable. Producer completion records a *result*, not reviewed Task satisfaction. A downstream Task consuming another role's contribution depends on that result **and its independent review gate** (bounded per-contribution gate, or preceding Wave gate when handoff is between Waves). A review Task is the named gate over other work, with independent reviewer attachment, evidence and pass/fail verdict; it cannot review its own output. If a Reviewer-authored deliverable must itself be checked, another eligible independent gate must be available or admission blocks. A Task's persistent `complete` transition occurs only when its bound result/decision and required gate/evidence are satisfied. Current `syncWorkTaskStatuses` must not mark a role Task complete just because a producer `loom_complete` returned. OQ answers/reconciliation may resolve narrow questions but cannot close a Task, user wait or gate. Answered blocking OQs retain per-consumer reconciliation; aggregate closure is not a prerequisite for an already reconciled consumer.
6. **Roll-up.** Scoped Wave review (`review-implementation` for a Worker-bearing Wave; truthful role-work Wave review when there is no Worker) depends on every bound Task and required earlier gate, then records an exact reviewed-Wave receipt covering full current-generation Task set and bindings. Do not infer completion from zero Worker steps or `plannedTaskSteps` returning empty. Claims release only after scoped PASS; later knowledge/Objective gates consume receipt rather than reclaiming Wave. Phase/Objective closure retains independent ancestor checks, Product Acceptance when applicable and final review. Planning-only PASS ends only its planning workflow and leaves Objective incomplete. User decision Task remains blocked until exact user-owned act is recorded; General/Reviewer prose is not a substitute.

### Concrete implementation seams

- Extend persistent Plan validation, amendment/history and projection in `plugins/loom/work.ts`: owner/responsibility and handoff survive revision reconstruction and focused/bounded Plan context. Do not use `write` as role inference.
- Extend `plugins/loom/tasks.ts` executable contract and `plugins/loom/workflow.ts` compiler/fingerprint/runnable/reopen handling; use one explicit binding lookup for status and lifecycle, not `task:<id>` prefix or Worker count as proof of role. Preserve existing Worker Task IDs for compatible newly admitted Worker paths.
- Change `plugins/loom/index.ts` `loom_task_plan`, attachment, `review-plan`, `loom_complete`, claim/sync/receipt, status and exact-role dispatch checks together; adjust `plugins/loom/lifecycle.ts` completion-history recovery and sidebar/dashboard projections. Bind receipt to role/gate graph as well as Task IDs. UI projections show accountable role, unmet decision/gate and blocked reason, but confer no authority.
- Keep control-plane persistence project-scoped and transaction/version fenced. Review gate must not PASS against executable fingerprint different from attachment. Dispatch grant uses *bound step role*, not caller's claimed identity; stale sessions and role impersonation fail at attachment/commit. Default artifact permissions and runtime elevation remain bounded by assigned role's authority.

## Coverage, failure and compatibility

- Routine Worker Task keeps `task:<id>` role and needs no extra specialist gate merely for ceremony; scoped Wave review still applies. Specialist producer → Worker in **same Wave** requires intermediate independent gate before Worker runs, not only final Wave review. Between Waves reviewed predecessor Wave receipt supplies edge. Role-only Wave is not a zero-Task Wave; its actual steps and scoped review count. Reviewer Task names output it independently judges. User decision/Anchor acceptance uses real user-authority record, not synthetic gate.
- Invalid owner, nonexistent/disabled role, unsupported responsibility, missing gate, ambiguous handoff, failed dispatch or unavailable user path: leave relevant work pending/blocked with exact cause; neither default to Worker/General nor auto-PASS. Recompile only unclaimed/unconsumed work after correction. Failed producer or denied grant cannot create satisfying receipt.
- Claimed Waves keep immutable admitted role/graph contract. Newly discovered authority work stops dependent progress and routes Plan amendment for still-unclaimed work; changed already-consumed premise requires invalidation/new generation or explicit compatible carry-forward proof. Reopen resets affected step attempts, dependent gates, evidence proof, Task satisfaction and Wave receipt; unaffected reviewed work remains historical. Concurrent claim attempts are serialized/version-checked; only one acquires exact Wave. Cancellation revokes new admission/grants but cannot erase in-flight operations or preserved evidence.
- Existing Worker-only claimed/completed Waves remain legible on historical contract. They are **not** migrated into specialist proof or silently converted to role-only execution. Previously unclaimed Plan Tasks lacking roles cannot be admitted by new compiler until Planner supplies roles in a fresh permitted revision and review succeeds. An old claim that cannot safely be reinterpreted remains historical; replan at next unclaimed boundary. Runtime version fencing prevents older writers from issuing Worker-only compilation into new role-aware state. An all-complete legacy Worker Wave is not evidence of a formerly unrepresented specialist decision.

## Invariants and falsification

| Guarantee and precondition | Enforcement boundary | Falsifying observation |
| --- | --- | --- |
| Each mandatory Task in admitted Wave has one current role/responsibility and exact supported slot/wait before claim. | Plan validator + compiler + `review-plan`/claim transaction. | Missing/disabled role or slot receives PASS/claim; owner inferred from write scope. |
| Receiving role never consumes unreviewed specialist result or invented user act. | Handoff DAG + independent gate/user-authority record + runtime runnable/Task transition. | Worker or General completion advances dependent Task while source gate/user wait pending. |
| Reviewed role output is attributed to current generation, Task, step attempt and independent gate. | Binding/receipt fingerprints + exact session attachment/completion. | Old OQ answer, step, Plan revision or stale session makes new Task complete. |
| No-Worker Wave and planning-only completion remain distinct from Objective completion. | Wave roll-up and Objective ancestor gates. | Empty Worker list auto-completes Wave/Objective or planning-only PASS starts execution. |
| Scope, project identity and concurrency cannot bypass authority. | Project storage, serialized claim, role-aware grants/mutation hooks. | Cross-project binding, competing claims, or Worker grant runs specialist slot. |

## Downstream proof and reconsideration

Implement deterministic control-plane tests plus real attached-tool integration for: whole-Plan planning-only feasible and infeasible *later-Wave* specialist paths; no Wave claim from planning-only PASS; routine Worker; Architect/Designer/Specifier/Documenter/General work without matching route-fixed step; Reviewer gate over producer; specialist → Worker same-Wave gate and cross-Wave receipt; exact user decision without agent impersonation; no-Worker Wave/Objective with applicable gates; unavailable role/missing independent gate; stale Plan/graph/review attachment; concurrent claims; reopen, cancellation, failed dispatch, old Worker-only history and no retroactive specialist credit. Assert persisted Task/step/role/gate/receipt state and actual dispatch denial, not just generated Plan text. Reconsider A only if measured bounded Wave limits or demonstrably safe reuse requires B, with equivalent isolation/compatibility proof. No unresolved product-policy choice is introduced by this technical design.
