No decisive probe is executed in this phase. Their results gate dependent implementation/rollout, not reviewed planning; Planner must place them ahead of that dependent work. Proven infeasibility goes to appropriate authority before silently weakening guarantees. Discovery can conclude with a structurally coherent recommendation and explicit early proof paths, not a claim these premises hold.

## Minimal feasible independent test realization

Choose a supervised **bubblewrap rootless Linux namespace policy**, replacing a bespoke namespace engine, rather than requiring the unfinished old OCI adapter. [Alternative/cost comparison](fact-model-and-continuity.md) treats rootless OCI and isolated VM as serious alternatives; package/kernel availability here is unproved. The trusted launcher uses a version/digest-attested substrate with an explicit policy outside plugin imports: empty mount root, fresh user/mount/PID/IPC/network namespaces, private synthetic HOME/XDG/runtime roots and approved read-only toolchain/source tree. Only finite approved copied source/fixtures and synthetic scratch enter; no production config/state, credentials, host home, shared Git metadata, engine/system-bus sockets or inherited arbitrary file descriptors are mounted/passed. Synthetic Git repositories are created inside. Network is disabled. Drop capabilities after namespace setup, set no-new-privileges, prohibit namespace escape/mount/ptrace/privilege-changing syscalls and host terminal injection using enforced seccomp/session separation. `/proc` describes only contained PID namespace; no host process/root handles. Descendants inherit policy and cannot migrate out of supervised process custody. Redirecting environment is defense in depth, never enforcement. Bubblewrap alone is explicitly not a complete sandbox policy.

The independent supervisor establishes and inspects restrictions **before** starting Bun/OpenCode or any product setup/import. It launches only after verifying namespace identities, mount allowlist, mapped UID/capability state, descriptor/socket allowlist, process-custody controls and applied policy. Missing substrate/unprivileged namespaces/toolchain/policy gives refusal before product execution. No implicit install/pull, rootful/setuid/ambient-host fallback or dependency on old adapter completion is accepted. Substituting OCI/VM requires Architect's equivalent boundary/operational decision and real provisioning authority. Availability on this host is unproven, not a local sandbox attestation.

### Synthetic-only evidence protocol

An outer witness creates a synthetic protected installation/sentinel outside the admitted inner mount tree. No live installation is discovered, opened or hashed. The child receives adversarial synthetic paths: direct absolute path, symlink traversal from allowed workspace, misdirected HOME/XDG and descendant helper. Probe opening synthetic protected data before plugin import, during setup and in a subprocess; require actual denied access or absent mount plus independently observed applied restriction. Record denial event/errno and containment identity. Witness reads only its own synthetic sentinel afterwards. Sentinel unchanged without access-restriction evidence is insufficient; successful container/process startup is insufficient.

Record source/host/toolchain/launcher/policy digest, synthetic target identity, pre-execution attestation, descendant evidence and bounded output. Include a preflight-refusal variant proving no child/import/setup event happened. Product logs cannot alone attest their own containment. Prohibit live DB comparisons even read-only. Test runner failure does not remove containment; supervisor retains control and captures process termination/unknown state. Synthetic host protocol tests use actual plugin/native hooks in this same boundary, not an ambient installed OpenCode session. No fake credentials or mocks may hide mandatory host admission paths; synthetic local effect servers can make lost-response behavior repeatable while remaining within containment.

## Controlled installation boundary

The one trusted custodian is shipped/accessible separately from plugin, with bounded dependency path and human-readable recovery manifest/export. Live manager, effect broker and offline recovery are modes/modules of this executable, not three services. Its stable SQLite journal uniquely owns installation identity, active paired code/data generation locator, monotonically increasing fencing token, ingress records and transfer/activation decisions. Derived manifest exports are checksummed read-only recovery aids, not another writable activation selector. Exclusive live/offline process lock plus journal transaction and FULL durability select exactly one generation. No damaged plugin schema flag is fence proof.

### Actual principals, handles and stock OpenCode participation

Threat boundary is untrusted/stale product code, stock tool subprocesses and their descendants—not a hostile kernel/root administrator or a human explicitly authorized to bypass installation controls. Trusted custodian runs as the owning host OS user outside product namespaces. Product processes map to that user's namespace UID but **do not inherit the host filesystem/process/network view**. Same-user mode bits/socket convention alone are insufficient; exclusion is enforced by namespace visibility, descriptor closure, seccomp and supervised process custody. Kernel/substrate and custodian/policy/IPC parser are in the trusted computing base. No new system UID/root privilege is required by the selected candidate; unavailable rootless/process-control prerequisites cause an owned wait.

- Only custodian and its bounded trusted SQLite/Git children hold writable DB, journal, workspace, repository/ref/config and generation handles. Before spawning product children, close all descriptors except assigned terminal/stdio and narrow endpoint descriptors; never pass directory/root/DB/object/ref/namespace/process-control handles. Product root contains read-only sealed approved inputs, writable private tool scratch and assigned IPC endpoint only. No host `/proc`, `/sys`, home, runtime directories, manager socket directory, shared repository or general network is mounted. Bind-mount read-only is not sufficient if an inherited writable FD remains; both must be checked.
- Launch each product authority compartment in its own namespace/process group with an external **delegated cgroup-v2 custody boundary** (or refusal if delegation/freezer/kill controls are unavailable). It contains all stock service/tool descendants; cgroup control files are not visible to them and delegation cannot be transferred. Custodian can freeze before sealing scratch, terminate/revoke a compartment and wait for actual empty/exit observation. PID namespace teardown supplies additional cleanup, not a guess that a tool return killed every descendant. Existing emitted remote effects are never considered stopped by cgroup kill.
- Stock OpenCode service, plugins and native tools run **inside** this compartment from first service startup, not merely a TUI attached to an unrestricted existing background service. Managed entry selects only the launched service/endpoint and approved fresh config; it cannot auto-discover/reuse a host service. Existing unrestricted service supplies no physical guarantee. Native edits operate on assigned scratch; actual native admission/output and custodian seal are composed as specified in [seams](realization-seams.md). Managed transport/native completion integration must withhold a **durable contribution acknowledgement** until custodian payload/receipt commit; an earlier tool-return observation can report scratch mutation only, not protected publication/completion. Failure preserves scratch and pending acknowledgement. This completion/transport participation is part of the early actual-stock-host proof, not permission to invent captured bytes from tool logs. The plugin integrates typed IPC, but cannot obtain raw managed-store access by importing SQLite or spawning shell. New native tools/hooks need no stock core fork as an assumption: actual supported hook/managed-service/endpoint participation is an early feasibility proof; if unavailable, stop/reopen this mechanism, never claim a cooperative hook is physical fencing.
- Each endpoint is launcher-bound to exact actor/work/attempt and kernel peer compartment (PID/start identity and supervised membership), with generation-scoped unforgeable request capability. Custodian checks peer identity as well as capability and exact target; supplied role/session strings cannot expand endpoint authority. No cross-compartment endpoint/FD passing is permitted. Different professional authority/independent reviewer needs a separately assigned compartment; a child session created inside the old service does not inherit another role's endpoint. Session handoff retains original history/context without granting broader custody. Endpoint protocol accepts bounded typed operations/observations, never arbitrary host paths, executable names, shell or raw SQL. Stale endpoint requests receive revoked-generation/attempt, while authorized late **observation intake** remains available for its original operation. Arbitrary event content is not trusted evidence without captured source provenance.
- Test compartments have no egress. Managed operational OpenCode can use a separately bounded trusted proxy endpoint for its approved provider/model and transport needs; no unrestricted host network, D-Bus, SSH agent, engine socket or credentials directory. Inference/transport routes cannot act as arbitrary external-effect tunnels. Remote mutation requires an exact broker operation/capability and retained invocation identity. Provider/stock-service compatibility and necessary proxy surface are explicitly unproven; no privileged network fallback is permitted. Actual spending/secrets/privileges must be separately authorized at their existing boundaries.

### Fence/write/invocation linearization

Custodian serializes generation/admission changes, canonical write transactions, Change-byte seals and **start of each trusted effect invocation** under one admission gate. It rechecks current work epoch/lease and active generation inside that gate; canonical reservation/charge commits durably before invocation. Before opening any effect handle/spawning the bounded executor, record durable journal invocation reservation. The actual spawn/write/ref syscall happens while the gate prevents a fence from interleaving; then append observed start/outcome. A crash in reservation→actual invocation gap is unknown, not evidence of nonexecution. The gate is released while external work runs; pause/cancel closes new starts without pretending existing effects ended.

Upgrade closes starts and freezes/revokes product scratch writers. Wait for bounded local canonical/Git writers to finish or terminate with observed outcome; close their handles before selecting another generation. No trusted executor may retain write access to an inactive/protected generation. Unknown remote operations may outlive activation and remain in stable ingress history; they cannot reopen local handles or create new admissions. Stale original product processes cannot bypass through retained descriptors because they never held protected ones; their scratch is frozen/revoked before candidate capture. Kernel bypass probes must test direct file opens, inherited-FD attempts, IPC role forgery, namespace/cgroup escape, raw network and manager/ref access, not only broker token rejection.

This is a new specified boundary, not evidence current plugin/process protections already enforce it. For the **first unmanaged cutover**, prior unconfined processes do have a different threat boundary; the offline bootstrap below must remove them before capture/activation.

## First cutover of unmanaged legacy state

Select a one-time **cold offline bootstrap** rather than relying on an advisory lock or guessed process-tree scan to revoke legacy writable FDs. A supported controlled cold start must establish that no pre-cutover local product/tool process survives (kernel boot/process-generation identity), disable automatic old OpenCode/plugin service startup, and keep new admissions closed until custodian capture is sealed. Trusted user/admin controls boot/service exclusion; starting old unmanaged writers invalidates that prerequisite. No reboot/service operation is authorized in this phase. This adds explicit one-time install coordination; later managed upgrades use the verified custody/fence path, not repeated cold restarts. A future cheaper freeze/revoke method may replace cold start only with equivalent legacy-handle exclusion proof.

Under that boundary, custodian captures a stable **legacy closure manifest** for relevant work, not arbitrary host files: source installation/project/repository identities, original database/export context and recovery code, HEAD/needed parent/ref/object closure; raw index and its entries including paths/modes/OIDs/conflict stages; actual working-tree versions/modes/symlink targets for changed/referenced files; required untracked and evidence/artifact bytes; original attempts/admissions/operation observations and any supplied source provenance. Stage S and worktree W may differ: store each separately with its locator and digest, including deletion/absence as a fact. Dangling required index objects are materialized before declaring closure. Exclude unrelated credentials/private host files; never omit protected acknowledged work merely because it is sensitive. Required sensitive payload preservation stays within exact authorized protected scope and confidential storage, not projection/log disclosure. Inability to identify required protected scope is a bounded inventory-owner question, not broad host scraping.

Read/verify each source version and closure under no-writer custody; commit captured payloads/manifest before acknowledgment; rehearse reconstruction into separate inactive directories/index and read-only historical retrieval **before source replacement**. Never overwrite one version with another to make the repository clean. Preserve original raw records and source labels; no new-style mutation receipt, contributor attribution or original PASS is minted. Old pending operation O retains original evidence/identity where supported, otherwise an explicitly unknown legacy-operation entry linking exact captured context. Cold local process termination is not remote undo; pre-bootstrap detached/remote effects remain unresolved until actual observation/nonduplicating reconciliation.

Classify independently: (a) bytes and original attribution verified; (b) bytes verified/recoverable, attribution or outcome unknown; (c) required acknowledged bytes physically missing/corrupt or closure incomplete. Category (b) satisfies **preservation**, but ownership-dependent current fulfillment/publication remains unproven until its authorized owner inspects/assesses or an actual accountable handoff/new contribution supplies the required fact. It does not block complete installation protection merely for lacking receipts that did not exist. Category (c) blocks a claim of complete cutover/recovery point; retain originals and name the specific recoverable-copy/inventory remedy, never fabricate bytes. Missing evidence alone cannot turn recoverable bytes into category (c).

Finite continuation for (b): stable original read -> `candidate-assessment` capability -> relevance/provenance/operation judgment using actual supported evidence -> still-unproven uses wait narrowly; isolate current new edits with fresh receipts and continue unaffected work. An actual handoff records current accountable custody, not backdated authorship. Unknown attribution cannot force every future upgrade to refuse; physical exclusion, closure and current-use proof are different predicates. Delivery P7 must exercise S≠W, conflict stages/untracked artifacts, an unknown contributor and old unknown operation, including offline restore/retrieval with no provenance adoption.

## Protected cut and upgrade protocol

1. Installation manager closes **all installation admissions** and fences canonical writers; per-workflow pause alone is insufficient. Serialize with admission/reservation and finish durable acknowledged commits. Capture cut sequence and every outstanding admitted operation. Prevent old physical processes from writing source/candidate generations; keep attributed later observation intake in a separate recovery spool while admissions remain closed.
2. Inventory protected closure: installation/project identities, accepted content/decisions, Plan revisions, lifecycle/leases/grants/resource consumption, attempts/original contexts/results, observation/claim payloads, questions/consumer treatments, reviews/acceptance, mutation/handoff/publication receipts, operation records and required recoverable artifacts. Include acknowledged uncommitted user contributions from managed custody, not only Git commits. If required workspace/artifact bytes cannot be frozen/copied/verified, protection is incomplete and upgrade cannot start.
3. Create consistent SQLite backups through supported backup mechanism under fenced cut of canonical database **and stable journal at its captured sequence/watermark**; never main-file-only copy while WAL may contain committed facts. BLOB payload/reference closure is inside those durable backups; include protected custody artifacts/legacy closure, compatible prior code/toolchain manifest, schema/identity and outstanding-operation inventory. Sync backup/generation files and their directory entries before committing manifest references in the stable journal. Independent read/integrity/digest/count/reference checks against synthetic protected cut are required.
4. **Before upgrade mutation**, restore backup into an inactive disposable generation with the prior compatible code, validate original fact families/relationships and safe admissions-closed readability. If restoration/completeness fails, do not start upgrade. Recovery-point verified receipt names cut, source/code identity and performed checks, not just file existence.
5. Stage code/schema conversion in an inactive candidate generation. Each migration transaction changes data, schema advance and success receipt together. Failure before commit leaves none of that transaction; previous committed steps can persist in candidate. Do not claim this is release rollback. Keep protected source and verified recovery point intact.
6. After candidate integrity/compatibility and fence checks, atomically activate code **and data generation** through one stable-journal transaction selecting the paired generation and fencing token; code loader resolves that committed selection, preventing mixed code/schema. Generation files/metadata must already be synced. Crash before/after selector commit chooses old/new pair, never two active writers. Admissions remain closed until actual post-activation checks and ingress/reconciliation boundary hold. A committed defective build can still require release recovery; successful activation is not acceptance.

New work admissions remain forbidden during upgrade; attributed late outcomes of previously admitted operations use the following journal custody, never an unacknowledged file append. The stable journal's ingress queue is the **spool**, not another service/object store.

### Durable spool and intake/import handoff protocol

**One intake endpoint persists across generations.** All irreversible invocation/outcome observations enter the stable journal before acknowledgement, both in normal operation and during recovery. Canonical observation/use indexes refer to original event IDs; they cannot independently edit the observed event. This modest ingress journal is not full event-sourced Plan/work authority. Generation switching transfers the importer, not the external producer endpoint; old producer callbacks can never target a restored canonical database directly.

Record contains installation, original operation/attempt/source epoch, source identity, source event ID and available per-source sequence/causal predecessor IDs, custodian ingress sequence, payload bytes/digest and observation kind. Identity is `(installation, original source binding, eventId)`; same ID/digest is the same intake receipt, same ID/different content is quarantined conflict with neither overwrite nor a second claimed outcome. For sources without stable IDs, custodian assigns an intake identity and labels any unresolved semantic duplicate uncertainty; equal text alone is not proof two remote effects were one.

| Boundary | Required commit/ack rule | Crash/full/conflict behavior |
| --- | --- | --- |
| Receive event | Under journal transaction, commit complete payload and original context/event identity with SQLite FULL before issuing durable receipt. File-backed temporary transport is not acknowledgment | Before/failed commit: no success ack; retain sender/recoverable scratch where available, surface owned capacity/I/O remedy, keep operation outcome unknown/unacknowledged. After commit/lost ack: query/retry **event submission with same identity**, not external effect; returns committed receipt |
| Import to generation G | In **one canonical transaction**, verify event digest; insert unique `importedIngress(eventId,digest,G)`, referenced payload/observation mapping and any consequential actual-consumption bookkeeping exactly once. No success/fulfillment is inferred from imported text | Crash before commit: replay. After commit/before journal transfer marker: query marker/digest and replay deduplicates. Same ID/different digest halts affected import as conflict; unaffected history survives |
| Confirm destination custody | Only after verified canonical commit and durable accessible generation/payload closure, append journal transfer receipt `(eventId,digest,G,canonicalCommitIdentity)` | Transfer marker without accessible destination never permits dropping sole custody. Restore to another G replays from preserved original journal with that G's import marker; a prior G marker does not claim new G imported |
| Retire pending queue item | Remove from pending scheduling only after destination custody confirmed; original immutable event/transfer history and payload remain retained/recoverable. This is not permission for physical deletion/GC | No deletion while the journal is sole acknowledged copy. Backup closure includes pending items, markers and original events. Any later retention policy needs its own authority/closure proof |

A FULL/sync/write failure closes new admissions requiring that resource before predictable loss; it does not convert actual remote completion to failure/no-effect, silently drop the observation or authorize remote retry. Host loss of unacknowledged delivery can leave unknown outcome honestly; accepted acknowledged records may not disappear. Disk repair/capacity/authorization waits have accountable owner and resumption condition.

Causal ordering: ingress sequence orders durable custody, **not external truth**. Import uses explicit operation/source/epoch relationships; per-source observed sequence gaps/predecessor gaps hold affected dependent use unproven until filled or independently resolved. Reordered terminal/start observations remain appended originals; a late 'running' event cannot overwrite a supported terminal outcome merely because it arrived last. Contradictory observations are retained and reconciled by authorized observer, not latest-arrival-wins. No universal external ordering/exactly-once guarantee is asserted.

Handoff: custodian closes importer G under admission gate, completes/rolls back its current canonical transaction, and commits a journal barrier B with source/intake watermarks and importer assignment. After restoring/activating Gnew, validate generation identity and replay all pending events through B, then commit importer assignment Gnew. Intake **continues durably into the same journal** throughout; events after B are processed by Gnew, including old-epoch observations. Under the same gate, verify all acknowledged events through B have destination custody or an explicitly retained unresolved dependency, and that every live source uses the journal endpoint; only then reopen work whose prerequisites are fulfilled. Later callbacks remain safe and visible without pretending operations quiescent. A stopped/unconfirmed source stays in outstanding-operation inventory; it does not block unrelated work solely because it can still report observations. Resuming affected effects requires their actual reconciliation.

Offline recovery acquires the same exclusive custodian ownership, stops old importer and never rewinds the live journal over newer acknowledged events. Restoring a damaged journal from protected backup requires first preserving/inspecting its newer raw custody and applying the existing loss/uncertainty boundary; backup validity does not justify deleting post-cut events. A recovery point includes journal sequence/closure in addition to canonical cut and paired code. These contracts preserve existing transaction-versus-release/newer-work/external-effect distinctions.

## Plugin-independent release/manual recovery

Standalone tool uses stable envelope/manifest and historical exports; it does not load/import the plugin, register tools, run automatic migrations or require its runtime. Offline instructions and compatible manager/code remain reachable outside Loom. Exact commands/runbook are downstream delivery documentation, not invented executable production steps here.

Inspect target identity, recovery cut, active/broken code and schema, all protected payloads, newer acknowledged work and outstanding effects. Fence writers/admissions before changing anything. Preserve the broken generation, recovery spool and newer raw envelopes in read-only quarantine with verified digests; never edit them to manufacture valid state. Wrong identity, corrupt/incomplete point, unsupported required format, disk/permission failure or inability to fence gives refusal with owned remedy. If inspection cannot establish delta, loss is unknown, not zero.

Restore into a **new inactive generation**, with matching prior code. Recover pre-cut acknowledged closure and retain later original history/spool under stable references. Do not blindly merge newer-schema facts into prior execution state. Where safe normalized import is verified it preserves both; otherwise retain attributable recovery history and mark current use unproven. Preview active-current-state losses separately from retained historical bytes. If activation would discard newer acknowledged work from current state, require actual specific user consent naming installation, target cut, delta and consequence. Hash that preview into decision; changed target/delta requires renewed consent. No response, stale consent or inability to disclose material loss refuses destructive activation; offer preservation/owned reconciliation, not an automatic reset. Keeping a quarantined file is not falsely advertised as zero loss of active progress.

Restore receipt records source/cut, user decision where needed, verification and actual activation outcome. Stable-journal paired-generation selection occurs only after code/state/fence/closure validation. Interrupted staging leaves originals active/intact and staging inspectable; interrupted activation is resolved by committed journal generation identity/digest, not rerunning mutation. Re-enter read-only first; import/reconcile retained custody, verify current contracts/proof and then reopen admissions. Original reviews remain original subject judgments, never fresh PASS.

**External effects are not restored.** Combine protected operation inventory, quarantined post-cut facts and recovery spool into an inspection history with deduplicated original identities. Missing outcome is unknown. Release restore uses a new generation/epoch and cannot replay old operation tokens. Before dependent effect execution, establish observed outcome or an authorized adapter strategy proven nonduplicating (for example query exact operation/ref or provider-supported idempotency); without it retain owned wait. Neither state restore nor consent to current-state loss authorizes repeating uncertain effects. Resource consumption is retained/reconciled from post-cut receipts, not reset to obtain free attempts.

## Publication incident regression: actual denial versus advertised authority

Run inside synthetic contained host with native permission hooks and the same control-plane interfaces, using disposable repositories; never reproduce against the staged adapter/user repository. Required trace:

1. Seed foreign staged/dirty contribution in shared destination; record its index/worktree/ref digest. Assign Designer/Specifier/Architect directory-subtree scope; admit native patch in assigned scratch with custodian seal to protected Change candidate, without exact-path workaround. Record base→output receipt under exact attempt/capability. Control-plane preflight and native hook report identical inputs/reasons.
2. Reserve exact P/T/D/C/F candidate; stage exact owned operands and hookless detached commit with those exact operands, separately exercising optional `--`. Both actual parser and native hook admit; observe actual commit parent/tree/delta/contribution chain under exclusive byte/config custody, not staged-snapshot assumption. Race scratch/candidate writes between validation and path commit: kernel/custody must prevent unauthorized W2 publication, not detect it only afterwards. Foreign shared destination bytes/index remain unchanged. Distinct integration races expected-old destination ref and must either win one conditional update or conflict without overwrite. Test a second linked worktree's shared-ref mutation; private custody cannot falsely claim linked refs independent. Valid publication must not require user manual commit or global index clearing.
3. Reviewer independently reviews exact artifacts; admits permitted status-only bookkeeping. Actual native patch emits the receipt consumed by staging. Scope elevation is neither necessary to reconstruct provenance nor misclassified product repair. Broader semantic edits are denied; status publication cannot grant self-review.
4. Negative contrasts: replace owned bytes after receipt, mix unknown foreign delta, replay old-attempt token, request arbitrary role/path, change ref before commit, and repair then ask same repairer for PASS. Deny exactly the missing predicate while preserving history/unaffected paths.
5. Kill between edit and receipt, before/after detached commit and before/after destination ref update with response lost; reconcile exact reserved operation/parent/tree/OID/ref history or report unproven/unknown without repeating effect. Never create provenance solely because the model says it wrote the file.

### Correction-specific recovery/enforcement falsifiers

- **Legacy bootstrap:** synthetic index S/worktree W/HEAD H all different, conflict-stage and required untracked versions, unknown contributor/old operation; no pre-bootstrap local writer survives the selected cold boundary. Capture/restore logic is proved inside the namespace fixture. The **cold-boot exclusion premise** additionally needs a disposable synthetic VM/installation boot observation with old service auto-start disabled and a pre-reboot stale writer/handle witness; resetting a fixture variable/process epoch on the same kernel is not boot proof. This is a bounded future proof fixture, not a VM production topology or permission to reboot the host. Missing safe VM/boot capability is an owned proof wait, never ambient fallback; include provisioning/disposal burden in the ledger. Complete raw closure restores each version offline with original labels; unknown provenance permits preservation but not fabricated fulfilled use. Remove one physically required acknowledged blob: completeness must refuse precisely that loss, not conflate it with unknown author.
